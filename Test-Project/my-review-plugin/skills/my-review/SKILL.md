# my-review — 코드 리뷰

변경된 코드에서 **실제로 깨지는 것**을 찾는다. 스타일 취향은 다루지 않는다.

## 1. 리뷰 대상 정하기

인자가 주어졌으면 그것을, 아니면 아래 순서로 자동 판단한다.

```bash
git rev-parse --is-inside-work-tree 2>/dev/null   # git 저장소인가?
git diff HEAD                                      # 맞으면 커밋 안 된 변경
git status --porcelain                             # 추적 안 되는 새 파일도 확인
```

git 저장소가 아니면 프로젝트의 소스 파일을 직접 읽는다. 대상이 3개 파일을 넘으면
먼저 파일 목록을 보여주고 우선순위를 확인한다.

**변경된 줄만 보지 말 것.** 바뀐 함수의 호출부, 그 함수가 읽는 상태, 그 상태를 바꾸는
다른 코드까지 읽어야 실제 버그가 보인다.

## 2. 무엇을 찾는가

우선순위 순서다. 위쪽을 먼저, 그리고 더 오래 본다.

### 정확성 (Correctness) — 최우선
- 경계값: 빈 배열, 길이 1, null/undefined, 0, 음수
- off-by-one, 인덱스 계산, 각도·좌표 계산의 부호
- 비동기 순서: 완료 전에 상태가 바뀌면? 이벤트가 두 번 발생하면?
- 상태와 화면의 불일치: 데이터를 바꾼 뒤 다시 그리지 않는 경로가 있는가
- 에러 경로: throw/reject가 났을 때 잠금(플래그, 로딩 상태)이 풀리는가

### 보안
- 사용자 입력이 `innerHTML`, `eval`, `document.write`로 들어가는가 (XSS)
- 하드코딩된 키·토큰·비밀번호
- 신뢰 경계를 넘는 입력의 검증 누락

### 리소스 / 생명주기
- `addEventListener` 후 제거되지 않아 중복 등록되는 리스너
- 타이머·인터벌·구독 정리 누락
- 요소를 다시 그린 뒤 옛 참조를 계속 쓰는 코드

### 유지보수성 — 마지막, 그리고 짧게
- 같은 로직의 3회 이상 중복
- 의도가 드러나지 않는 이름
- 주석과 실제 동작의 불일치

### 다루지 않는 것
들여쓰기, 따옴표 스타일, 세미콜론, 줄 길이, 개인 취향. 포매터의 일이다.

## 3. 판단 기준 — 이게 핵심이다

발견한 것마다 **구체적인 실패 시나리오**를 쓸 수 있어야 보고한다.

> 입력 X일 때 → Y 줄에서 → Z가 일어난다

시나리오를 못 쓰겠으면 그건 발견이 아니라 느낌이다. 보고하지 않는다.
"~할 수도 있다", "일반적으로 권장된다" 같은 표현이 나오면 근거가 없다는 신호다.

발견했다고 생각한 것은 **코드를 다시 읽어 확인한다.** 이미 처리하고 있는 경우가 많다.

## 4. 보고 형식

심각도 높은 순으로 정렬한다. 파일:줄 을 반드시 붙인다.

```
### [심각] index.html:311 — 회전 중 메뉴 삭제 시 결과 불일치
회전이 4초 동안 진행되는 사이 메뉴를 삭제하면 menus 배열의 인덱스가 밀린다.
transitionend 시점에 menus[i]를 다시 읽으므로 원판이 멈춘 조각과 다른 이름이 표시된다.
→ 재현: START 클릭 후 2초 안에 아무 메뉴나 × 클릭

수정: spin() 시작 시 당첨 이름을 지역 변수에 복사해두고 그 값을 표시한다.
```

심각도 구분:
- **심각** — 잘못된 결과가 나오거나 죽는다. 지금 고쳐야 한다
- **주의** — 특정 조건에서만 깨진다. 고치는 게 맞다
- **제안** — 동작은 맞지만 나중에 문제가 될 구조

문제가 없으면 **없다고 말한다.** 억지로 채우지 않는다. 대신 무엇을 확인했는지 한 줄로 남긴다.

## 5. 마무리

발견을 나열한 뒤 이렇게 묻는다:

> 고칠까요? 번호를 알려주시면 해당 항목만 수정하겠습니다.

**묻기 전에 코드를 수정하지 않는다.** 리뷰와 수정은 분리한다.
